## 0. 执行摘要（TL;DR）

AgentFlow 当前已完成 **v0.2.0 桌面版**（单用户、本地、Electron + FastAPI + React），具备了 AI 工作流编排的核心引擎能力（DAG 调度、8 类节点、过程可观测性、多模型适配）。

**从本地到 SaaS 的战略跃迁需要 3 件事：**

| 维度 | 当前状态 | SaaS 需要 | Gap 规模 |
|------|----------|-----------|----------|
| **产品形态** | 单用户桌面应用 | 多租户 Web SaaS + 可选私有化 | 全新架构（~70% 代码需适配/重写） |
| **用户画像** | 独立开发者、个人效率工具爱好者 | 企业 IT 管理者、业务团队负责人、AI 应用团队 | 从"个人"到"组织"的范式转移 |
| **商业模式** | 无 | 混合（SaaS 订阅 + 私有化授权 + Token 分成） | 从零设计定价、计费、计量体系 |

**推荐路径："开源自托管优先 + 云 SaaS + 企业私有化"三轨并行**

- Phase 1（现在 → Q1）：把桌面引擎 Web 化 + 增加多租户基础 → 发布 Open Core
- Phase 2（Q1 → Q2）：完善协作/权限/计量/计费 → 云 SaaS 公测
- Phase 3（Q2 → Q3）：企业级能力（SSO/SAML、审计日志、私有化部署）→ 签约首批企业客户

**核心差异化定位："企业级 AI 工作流编排的可观测性内核"**——n8n 和 Dify 做得很大很全，但在"过程可观测性"这件事上没人做到 AgentFlow 这么深（每个节点输入可见、变量解析快照、运行对比 diff、失败原因分类）。这是我们已有的、应放大的差异化支点。

## 1. Phase 1 — Discovery：市场扫描与竞品分析

### 1.1 市场全景

AI 工作流编排/自动化赛道目前呈现三股势力：

| 类别 | 代表 | 核心价值 | 商业模式 | 规模信号 |
|------|------|----------|----------|----------|
| **传统自动化 + AI 扩展** | n8n, Make, Zapier | 连接一切 SaaS，AI 作为一个节点 | 开源自托管 + 云 SaaS + 企业版 | n8n: $240M 融资、$2.5B 估值、$40M+ ARR、6× 用户增长 |
| **AI 应用构建** | Dify, LangFlow, Flowise | Chatbot + RAG + Agent 可视化构建 | 开源 + 云 SaaS | Dify 近 2 万 Star；LangFlow 被 IBM/DataStax 收购 |
| **企业 Agent 平台** | Salesforce Agentforce, ServiceNow AI Agents | 嵌入 CRM/服务台的 AI Agent | 企业 SaaS，$15K-$500K+/年 | Salesforce Agentforce 是其核心战略方向 |

### 1.2 竞品深度对比（按 AgentFlow 的差异化维度）

| 维度 | n8n | Dify | LangFlow | **AgentFlow（当前）** | **AgentFlow（SaaS 目标）** |
|------|-----|------|----------|----------------------|--------------------------|
| **过程可观测性** | 执行日志 + 节点详情 | 运行日志 + Token 消耗 | 节点输出 | ✅ **节点输入/输出/错误对比/版本历史** | 分布式运行追踪 + 协作评论 + 审计 |
| **执行引擎** | 自研工作流引擎 | Python + Celery | LangChain/LangGraph | ✅ **自研 DAG（RunManager + Kahn + semaphore）** | 分布式引擎 + 队列化 + 并发隔离 |
| **模型适配** | 70+ App 集成（含 LLM） | 多模型 + RAG 向量库 | 100+ LangChain 组件 | ✅ **OpenAI/Ollama/Anthropic 三适配器** | LLM Gateway + 自定义模型 + 成本路由 |
| **数据安全** | 凭证隔离 + 自托管 | 私有化部署 | 私有化部署 | ✅ **本地密钥加密 + Fernet** | 企业级密钥管理 + 审计 + 私有化 |
| **协作能力** | 企业版有 RBAC + 共享 | 企业版有团队空间 | ❌ | ❌ 单用户 | 实时协作 + 版本 Review + RBAC |
| **定价模式** | 云 SaaS（按操作数）+ 企业（按席位） | 云 SaaS（按 Token）+ 私有化 | 开源免费 | 无 | SaaS（按工作流数/运行次数）+ 私有化 |

### 1.3 竞品弱点 → AgentFlow 的机会

| 竞品 | 明确弱点 | AgentFlow 可切入的价值 |
|------|----------|----------------------|
| **n8n** | 复杂工作流成本爆炸（按操作数计费）；AI 能力是"附加"而非核心 | AgentFlow 把 AI 作为一等公民，定价不随复杂度线性爆炸 |
| **Dify** | 工作流引擎是"为 Chatbot 服务"的，不是通用 DAG；审计和可观测性较弱 | AgentFlow 是纯粹的 DAG 编排引擎，可观测性深度碾压 |
| **LangFlow** | 强依赖 LangChain 组件生态；运行时可移植性差 | AgentFlow 自研引擎不绑定任何框架，用户可自由定义节点 |
| **共同痛点** | 几乎所有竞品的"过程可观测性"都停留在"输出结果"，缺少"输入快照 + 变量解析 + 失败根因分类" | **这是 AgentFlow 的最强差异化，应成为核心卖点** |

### 1.4 目标市场规模（TAM/SAM/SOM 估算）

| 指标 | 估算 | 依据 |
|------|------|------|
| **TAM（总可寻址市场）** | $5-8B（2026） | AI Agent Orchestration Platforms 市场 2034 预计 $50B+，CAGR 30%+ |
| **SAM（可服务市场）** | $800M-1.2B | 专注"可观测 AI 工作流编排"的细分（排除 CRM 嵌入型产品） |
| **SOM（可获得市场）** | 首年 $0.5-1M，3 年 $5-10M | 先从国内中小企业 + 海外开发者切入，建立市场地位后拓展企业 |

### 1.5 关键发现（Discovery Insight Summary）

1. **"过程可观测性"是差异化王炸**：n8n、Dify、LangFlow 都做了工作流引擎，但 AgentFlow 已有的"节点输入可见 + 变量解析快照 + 运行对比 diff + 失败原因分类"这套组合拳，竞品没一个做全。
2. **数据安全 = 非功能变核心卖点**：中国市场金融/政务/大企业有硬性"数据不出域"要求，私有化部署不是选项而是入场券。
3. **"AI 为核心"的工作流 vs "连接为核心"的工作流**：n8n 是后者（连接一切 SaaS），Dify 是前者（AI 应用构建）。AgentFlow 应定位于"AI 原生 DAG 引擎"——既支持纯 AI 工作流，也支持 AI + HTTP + 脚本的混合。
4. **定价陷阱要避开**：n8n 按操作数计费导致复杂工作流成本爆炸；Dify 按 Token 计费让用户不敢用量。AgentFlow 应探索"平台费 + 用量封顶"或"按工作流版本数"的混合模式。

## 3. Phase 3 — 产品战略：定位、商业模式、差异化

### 3.1 产品定位陈述（Positioning Statement）

> **AgentFlow** 是一个**面向企业 AI 应用团队的可观测 DAG 编排引擎**，帮助他们把复杂的 AI 处理流程从"脚本堆"升级为"可观测、可协作、可审计"的生产系统。
>
> 与 n8n（连接优先）、Dify（Chatbot 优先）、LangFlow（LangChain 绑定）不同，AgentFlow 以 **"AI 原生 + 过程可观测性深度"** 为核心差异点——我们把工作流中每一步的输入、变量解析、错误分类、运行对比都做到了极致可见，让团队能快速定位问题、持续优化、放心上线。

### 3.2 价值主张

| 目标用户 | 核心价值承诺 |
|----------|-------------|
| **AI 应用团队** | "让你的 AI 系统像传统软件一样可观测、可调试、可维护" |
| **业务自动化负责人** | "把 AI 工作流的成本从'随复杂度爆炸'变成'固定月费随便用'" |
| **独立开发者** | "一个不绑定 LangChain 的纯 DAG 引擎，适合做复杂 AI 编排" |

### 3.3 差异化锚点（Unique Value Props）

1. **可观测性深度 —— 竞品无人能及**
   - 节点输入 + 变量解析快照（不只是输出）
   - 失败自动分类（鉴权/网络/超时/脚本/变量/JSON）+ 修复建议
   - 两次运行节点级 diff 对比
   - 运行关联版本历史，任何运行都能回溯"当时用的哪版 prompt"

2. **AI 原生 DAG —— 不绑定 LangChain / Chatbot 场景**
   - 自研引擎，节点完全可定制
   - 既支持纯 AI 工作流，也支持 AI + HTTP + 脚本 + 条件的任意组合
   - 模型无关：OpenAI / Ollama / Anthropic / 自定义端点

3. **三轨商业模式 —— 用户自由选择部署方式**
   - 开源版（自托管，免费）—— 生态入口
   - 云 SaaS（托管，按席位/工作流数收费）—— 收入主力
   - 企业私有化（授权 + 年服务费）—— 大客户专属

### 3.4 商业模式设计

#### 定价模型

| 版本 | 目标用户 | 价格 | 核心功能 |
|------|----------|------|----------|
| **Community（开源）** | 独立开发者、早期团队 | 免费 | 单用户、桌面/Web、8 类节点、过程可观测、基础版本历史 |
| **Pro（云 SaaS）** | AI 应用团队、成长型公司 | $49/用户/月 或 $299/工作流/月（二选一） | 多用户协作、RBAC、运行对比、定时触发、AI Gateway（成本路由）、优先支持 |
| **Enterprise（私有化）** | 金融/政务/大企业 | $15K-$50K 年费（含支持） | 私有化部署、SSO/SAML、审计日志、无限存储、专属服务、定制化节点 |

#### 收入构成假设（Year 2）

| 来源 | 占比 | 说明 |
|------|------|------|
| 云 SaaS 订阅 | 50% | 主要增长引擎 |
| 企业私有化授权 | 30% | 高客单价 |
| 增值服务（模板市场、定制节点、培训） | 15% | 社区变现 |

## 4. Phase 4 — 问题框架与解决方案树

### 4.1 问题假设（Problem Hypothesis）

> **我们相信**，企业 AI 应用团队在把 AI 处理流程从"脚本堆"迁移到"生产系统"时，**最大的障碍不是写不出流程**，而是**不知道怎么调试、怎么协作、怎么放心上线**——现有的工作流编排工具（n8n、Dify、LangFlow）在可观测性深度上都停留在"能跑但看不清"的水平。
>
> **如果我们能**提供一个以"过程可观测性"为核心的 DAG 编排引擎，把每一步的输入、变量解析、错误分类、版本对比都做到极致可见，**那么**这些团队会愿意从现有工具迁移过来，并把 AgentFlow 作为他们 AI 工作流的标准基础设施。

### 4.2 解决方案机会树（Opportunity Solution Tree）

```
客户问题："AI 工作流出了问题但我看不清过程"
│
├─ O1: 让运行过程每一步都可见
│   ├─ S1.1: 节点输入落库 + 变量解析快照 ← AgentFlow 已实现（F1/B3）
│   ├─ S1.2: 分布式运行追踪（跨服务 Span/Trace）
│   └─ S1.3: 实时变量值变化（类似 LangSmith 的 trace view）
│
├─ O2: 让失败快速可定位可修复
│   ├─ S2.1: 错误自动分类 + 修复建议 ← AgentFlow 已实现（F1）
│   ├─ S2.2: 失败后自动诊断流程（"要不要换模型？"）
│   └─ S2.3: 一键重试（只重试失败节点）
│
├─ O3: 让多人协作不混乱
│   ├─ S3.1: 版本 Review + 审批流程
│   ├─ S3.2: 实时协作（类似 Figma）
│   └─ S3.3: 运行日志评论与 @mention
│
└─ O4: 让成本可控可预测
    ├─ S4.1: Token 预算告警
    ├─ S4.2: 成本路由（自动选最便宜的能完成任务的模型）
    └─ S4.3: 固定月费模式（不按操作数计费）
```

## 5. Phase 5 — 优先级排序

### 5.1 框架选择：RICE + Kano 混合

**适用依据（来自 prioritization-advisor）：**
- **产品阶段**：Pre-PMF → Early PMF（寻找 SaaS 付费意愿，有少量桌面用户基础）
- **团队背景**：小团队（单人或 2-3 人），从本地应用转向 SaaS
- **核心挑战**：太多功能要做（多租户、协作、计费、部署……），需要聚焦
- **数据可用性**：有桌面版的使用数据基础，但无 SaaS 付费数据

**为什么用 RICE + Kano 混合：**
- 用 **Kano** 区分"基本功能 vs 性能功能 vs 差异化功能"——避免把"登录注册"当成核心竞争力
- 用 **RICE** 在同类别内排序——数据驱动，透明

### 5.2 Epics 定义与 RICE 评分

| Epic | 假设（Hypothesis） | Reach（月触达） | Impact | Confidence | Effort（人月） | RICE 得分 | Kano 分类 |

## 7. Phase 7 — 核心用户故事（SaaS 转型版）

### US-001：注册与首次体验

> **Summary：新用户 5 分钟内从注册到跑通第一个 AI 工作流**

```
As a 第一次使用 AgentFlow 的 AI 应用团队成员
I want to 用邮箱快速注册，进入后立刻看到可运行的模板
so that 我不用花时间搭环境就能体验 AgentFlow 的核心价值

Given 我是一个新用户，之前没注册过 AgentFlow
and Given 我访问 AgentFlow 官网
When 我输入邮箱和密码完成注册
and 我选择"使用模板创建"而非空白开始
Then 我在 5 分钟内能看到一个 AI 模板运行出结果
and 我能看到每一步的输入、输出和 token 消耗
```

### US-002：团队协作与权限

> **Summary：AI 团队多人协作，不同角色看到不同操作权限**

```
As a AI 应用团队的 Leader（Owner 角色）
I want to 把工作流分给团队成员，每个人只能做他该做的事
so that 我不用怕不小心有人改坏了生产环境的工作流

Given 我们团队有 5 个人（2 个开发者、2 个运营、1 个我）
and Given 我已经创建了团队工作空间
When 我邀请 2 个开发者为 Editor、2 个运营为 Operator
Then 开发者能编辑工作流但不能删除工作空间
and 运营只能运行已发布的工作流不能编辑
and 我能在审计日志里看到所有人的操作记录
```

### US-003：失败根因定位

> **Summary：运行失败后，系统自动分类原因并给出修复建议**

```
As a AI 应用团队的开发者
I want to 工作流失败时系统告诉我"为什么失败、去哪改"
so that 我不用逐节点翻日志就能定位问题

Given 我的工作流已经运行了 N 次，这次突然失败了
and Given 失败节点的错误是"HTTP 401 Unauthorized"
When 我打开运行详情页面
Then 失败节点自动展开并置顶
and 错误被分类为"鉴权失败"，并给出建议"请检查 API Key 是否过期"
and 我能一键跳转到模型配置页面去验证
```

### US-004：版本对比与回滚

> **Summary：生产环境出问题时，一键回滚到上周稳定版本**

```
As a 负责生产环境稳定性的 AI 团队成员
I want to 把工作流回滚到某个历史版本，并对比版本差异
so that 我能快速定位"这次质量下降是不是因为 prompt 改了"

Given 我们的"竞品分析"工作流上周还能稳定输出，今天质量突然下降
When 我打开该工作流的版本历史，选择上周的稳定版本预览
Then 我能看到两个版本在 prompt 内容、节点配置上的 diff
and 我点击"恢复此版本"后，系统自动生成一个新版本（不删除历史）
and 恢复后运行能输出和上周一样的结果
```

### US-005：AI Gateway 成本控制

> **Summary：每月 Token 预算不超标，复杂工作流也不怕成本爆炸**

```
As a AI 应用团队 Leader
I want to 设置月度 Token 预算上限，并在快超支时收到告警
so that 我不会因为一个意外的工作流循环导致预算爆炸

Given 我们团队月度 Token 预算是 $500
When 我在 AI Gateway 里设置了 $400 的告警阈值和 $500 的停机阈值
and 某天一个工作流意外循环消耗了 $380

and 如果继续运行到 $500，系统自动暂停该工作流的后续运行
and 我能在 AI Gateway 面板里看到每分每秒的实时消耗
```

### US-006：私有化部署

> **Summary：大企业客户一键私有化部署，数据完全不出域**

```
As a 金融科技公司的架构师

```

| 风险 | 可能性 | 影响 | 应对策略 |

| **技术债务：多租户改造触碰引擎核心** | 🔴 高 | 🔴 高 | AgentFlow 引擎已做了良好的模块分层（core/ + modules/），tenant_id 隔离可通过中间件 + SQLAlchemy session 注入实现，不碰引擎核心逻辑 |
