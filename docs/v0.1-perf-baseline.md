# v0.1 性能基线 · 100 节点

> 对应 backlog **B1**（M2 遗留："100 节点性能基线"从未压测）。
> 目标来自 roadmap M2 验收：**拖拽 ≥ 30fps、运行不阻塞 UI**。

## 1. 怎么测

| 层 | 位置 | 测什么 |
|---|---|---|
| 前端（真实浏览器） | `e2e/perf100.spec.ts` | 100 节点画布拖拽帧率；运行期间主线程长任务 |
| 后端（调度器） | `apps/api/tests/test_scheduler_scale.py` | 100 节点图在并发闸门下的完成时间与结果完整性 |

复现：

```bash
pnpm e2e                                   # 含 perf100.spec.ts（先 build:web）
uv run --directory apps/api pytest -q tests/test_scheduler_scale.py
```

前端用例的图结构：1 个输入 + 99 个输出全部直连输入（100 节点 / 99 条边）。
这样运行时只有一层并行，压的是画布渲染与 SSE 状态更新，而不是模型延迟。

## 2. 实测（2026-11-01，Windows 11 / Node 22.23.4 / Chromium headless）

| 指标 | 实测 | 阈值（回归闸门） |
|---|---|---|
| 100 节点拖拽帧率 | **62–64 fps**（两次实测 62.6 / 63.8） | ≥ 30 fps |
| 运行期间长任务（>50ms）数量 | **0 个** | — |
| 运行期间最长单任务 | **0 ms** | < 1000 ms |
| 100 节点调度完成时间 | **4 ms**（本地） | < 5 s |

> 说明：headless Chromium 的 rAF 通常锁 60fps，62.6fps 是因为统计窗口内
> 有少量零间隔帧；这已经代表"满帧"。阈值定 30fps 是为了在 CI 机器更慢、
> 或有 1-2 帧抖动时不误报，同时能拦住"掉到十几帧"的性能回归。

## 3. 阈值为什么这么定

- **30fps 而不是 60fps**：跨平台 CI（ubuntu-latest 共享 CPU、无 GPU）无法保证
  60fps；30fps 是"拖拽手感可用"的下限，也是 roadmap 的原始验收线。
- **长任务 1000ms**：超过 1s 的主线程阻塞会让运行面板明显"卡住一下"。
  实测为 0，说明 SSE 逐事件更新没有引发布局风暴；留 1s 余量避免偶发 GC 误报。
- **后端 5s**：100 个节点、4 并发、纯内存执行，真实耗时毫秒级；5s 只用于
  拦住"调度退化成 O(n²) 或串行"这类结构性回归。

## 4. 结论

- B1 的两条验收（拖拽帧率、运行不阻塞 UI）**有可重复的自动化基线**，
  并且已接入 PR 级 CI（`.github/workflows/ci.yml` 的 `e2e` job）。
- 后续任何改动只要让拖拽掉到 30fps 以下、或运行期间出现 >1s 长任务，
  CI 会直接失败，而不是靠"感觉变卡了"。
- 真实 provider 的网络延迟不在本基线范围内（那个问题由超时与取消机制覆盖）。
