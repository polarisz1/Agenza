# AgentFlow 观测层 Pivot · 验证计划（GO/NO-GO）

> **决策背景**：2026-11-06 商业价值重评估结论——横向平台路径无法与大厂应用层竞争（差异化是"留存型"而非"获客型"，迁移成本必输）。选定路径 A：转向"AI 工作流观测/治理层"（LangSmith 模式）。
> **本计划性质**：验证方案，不是开发计划。**验证通过前冻结一切新功能开发。**
> **周期**：2 周（2026-11-06 → 2026-11-20）

---

## 1. 新问题假设

> **我们相信**，在 Coze / Dify / n8n 上跑生产级 AI 工作流的团队，当运行失败或输出质量下降时，平台自带的日志不足以快速定位根因，也不支持跨运行的版本治理与成本归责，导致他们每月为此付出数小时以上的排查和返工代价。
>
> **如果我们能**提供一个中立的第三方观测层——接入他们的运行数据，给出深度根因诊断、成本归因、版本对比与审计报告——**那么**其中一部分团队愿意为它付订阅费。

## 2. GO/NO-GO 门槛（量化，不满足即止损）

| # | 前提 | 通过标准 | 验证手段 |
|---|------|----------|----------|
| **P1 痛点真实性** | 平台自带观测"不够用"是真实且高频的痛 | ≥5/8 访谈者过去 30 天内真实遭遇过"靠平台日志定位不了问题"，且单次排查耗时 ≥1h（凭记忆陈述具体事件，非假设） | 访谈 |
| **P2 数据可得性** | 至少 2 家平台能稳定拿到运行级数据 | Coze / Dify / n8n 中 ≥2 家：API 或导出可获取节点级执行数据，且用户愿意授权接入 | 技术侦察（见 §5）+ 访谈确认授权意愿 |
| **P3 付费意愿** | 有真实付费信号，不是口头"不错" | ≥3/8 出现行为信号：愿意留联系方式约试用 / 愿意提供真实运行数据做 Concierge 分析 / 主动询问价格 | 访谈 + Concierge 实验（§6） |

**NO-GO 规则**：任一前提不满足 → 执行路径 D 止损（保留桌面版与代码资产，暂停投入，1-2 季度后复审）。**不允许"门槛差一点但感觉有戏"式放水。**

## 4. 访谈脚本（Mom Test：只问过去行为，禁止假设性问题）

1. 你现在在哪个平台上跑工作流？跑了多久？大概多少条、什么场景？（暖场 + 资格确认）
2. **上次工作流出问题是什么时候？** 具体讲讲那次：什么现象、你第一步做了什么、花了多久定位、最后原因是什么？（核心题：P1 证据）
3. 当时平台自带的日志/追踪给了你哪些信息？缺了哪些信息让你多花了时间？
4. 定位出来后你怎么改的？怎么确认"改完就好了"？有没有出现过"改了 A 反而坏了 B"？
5. 你们怎么向老板/客户交代一次工作流事故？需要什么数据？（成本归因/审计痛点）
6. 每月花在工作流排查上的时间大概多少？这类事故对业务的影响是什么？（痛的标价）
7. 有没有试过把运行数据导出来自己分析？怎么做的？（数据授权意愿 + 现有 workaround）
8. （收尾）如果有一个工具能接你现在的平台、自动给出这类诊断报告，你会希望它怎么做？（此时才允许谈概念）

**打分规则**：P1 = 第 2/3/6 题出现具体事件+时长；P3 = 结束后 48h 内的行为（回消息/交数据/问价格），口头兴趣不计分。

## 5. 技术侦察 · 初步结果（2026-11-06）

| 平台 | 数据可得性 | 已确认 | 待验证（W1 PoC） | 风险 |
|------|-----------|--------|------------------|------|
| **Coze** | 🟡 部分可得 | 对话消息 API（含 function_call/tool_response 中间态）；工作流异步运行结果 API（execute_id）；付费套餐支持消息导出 CSV（免费版不行） | 节点级粒度：API 返回的是"对话/运行"级还是"节点"级数据 | 免费版无导出 → 目标用户需付费版 |
| **Dify** | 🟡 部分可得 | 三层观测（logs/tracing + 系统趋势）；Workflow log archives 按月归档下载（**企业版专属**）；审计日志 CSV（企业版）；文档显示已含"Variable Snapshots: 每步变量状态" | Community 版 API 拿节点级数据的实际粒度 | ⚠️ **重大风险信号：Dify 已把变量快照做进产品**，我们"节点输入快照"的差异化主张正在失效 |
| **n8n** | 🟢 可得 | Executions API 长期存在，运行级数据可拉取 | 节点级 input/output 的完整度 | 相对最低 |

**侦察结论对假设的影响**：P2 大概率成立（三家都能拿到数据），但 **P1 的难度上调**——Dify 在 2026 已把观测当成卖点在补（甚至只放在企业版收钱），说明两点：(a) 平台自己认定这是付费点，第三方层有价格锚；(b) 留给"数据比平台全"的空间收窄，我们的访谈必须重点问"**平台有这些功能你为什么还不够用**"，而不是"你需要观测吗"。

## 6. Concierge 实验（最小付费验证）

- **做法**：请 2-3 个访谈者导出他们平台最近一个月的真实运行数据（CSV/JSON），我们**人工**套用 diagnosis.py 的 13 类规则分析，48h 内交付一份"工作流健康诊断报告"（失败根因 Top N、成本归因、可优化点）。
- **观察**：(a) 愿不愿意交数据（授权意愿）；(b) 报告是否命中他们已知/未知的问题（价值感知）；(c) 是否主动问"这个能不能自动/多少钱"（付费信号）。
- **成本**：人工 + 现有 diagnosis 逻辑，零新开发。这一步同时验证 diagnosis.py 资产的可迁移性。

## 7. 若 GO：产品形态预设与资产映射

形态：**接平台数据的 SaaS 观测层**（ingest adapter → 诊断引擎 → 报表/告警/审计），AgentFlow 画布保留为可选组件。

| 现有资产 | 迁移后角色 | 复用度 |
|----------|-----------|--------|
| diagnosis.py（13 类根因规则） | 产品核心引擎 | 高 |
| 运行 diff / 节点输入快照 UI | 报告呈现层 | 高 |
| AI Gateway 预算/成本分析 | 成本归因模块 | 高 |
| 版本治理 + 审计中间件 | 治理/合规模块 | 中高 |
| 多租户 + auth + workspace 地基 | 多平台数据接入的租户体系 | 高 |
| 工作流画布/执行引擎 | 降级为可选组件，停止投入 | — |

## 8. 对现有开发节奏的影响（即日生效）

1. **冻结 Sprint 4/5**（计费、Stripe、模板市场、部署包）——不投入一行代码
2. 工作区未提交的变更（子工作流、诊断、nodeHierarchy）**只做收尾提交**，不开新分支功能
3. 画布类新功能全部停止；仅接受观测/诊断相关的小修
4. W1 PoC（三平台数据拉取脚本）放 `tools/recon/`，属验证资产非产品代码
